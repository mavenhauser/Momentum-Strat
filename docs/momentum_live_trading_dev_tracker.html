Bugs found — only surfaced under live conditions, not in review

BUG 1

IBKR client-ID collision (Error 326)

Symptom
Every cron-triggered run of the live trader failed at client.connect() — "Unable to connect as the client id is already in use."
Root cause
run_paper_trader.py (SPX Scalp) holds clientId=1 continuously all session; the momentum trader defaulted to the same ID since none was ever assigned.
Fix
Distinct client IDs added to config: 45 (live trader), 46 (smoke test), 47-57 used ad hoc for diagnostics.
BUG 2

Price-reasonability collar rejection (Error 202)

Symptom
Orders submitted then immediately auto-cancelled. An early red herring (Error 10349, "TIF set to DAY") looked like the cause but wasn't.
Root cause
The shared MARKETABLE_LIMIT_SLIPPAGE_PCT (10%, tuned for SPX 0DTE options) is far more aggressive than IBKR's price-collar tolerance for a normal equity option (~3.5% observed on a live DELL test).
Fix
New MOMENTUM_LIMIT_SLIPPAGE_PCT = 0.03, scoped to the momentum system only — the shared SPX constant was deliberately left untouched since it's unverified against this same collar and the SPX trader is already live.
BUG 3

TWS order-processing stall

Symptom
A live DELL close order sat at "Submitted"/no-response indefinitely across 3 separate attempts (minutes each) despite reads (positions, NLV, quotes) working fine and fast throughout.
Root cause
TWS's own order-processing got stuck — consistent with prior project history (docs/paper_trading_dev_tracker.html) of "Error 322: Maximum number of account summary requests exceeded" after prolonged uptime, visible cycling in paper_trader.log at the same time.
Fix
Manual TWS restart. Not a code fix — this is an operational hazard to watch for, not something the scripts can self-heal.
ONGOING

Cron not reliably firing at all

Symptom
Zero confirmed successful unattended cron-triggered runs as of 2026-08-06, across multiple trading days. Every successful run has been a manual invocation.
Root cause (suspected)
The MacBook cycling into "Maintenance Sleep" every 15-90 min while on battery + Low Power Mode + standby — cron cannot fire while the OS is suspended, and this produces no error, nothing logged, the tick is just silently skipped. Confirmed real (not just theory) via pmset -g log showing near-continuous sleep cycling through a full trading day.
Fix
User to keep the machine plugged in / Low Power Mode off during market hours. Not yet confirmed resolved — no full trading window has completed under "plugged in" conditions with a clean result yet.
Also discovered, unrelated to any of the above: another session/actor has been working on the SPX Scalp system in parallel in this same repo (rewrote get_quote() to use DXLink, added several new signal modules, a launch_paper_trader_if_needed.py reliability script). Confirmed via file-watcher diffs showing up mid-session that weren't authored here. The 2026-08-06 commit was carefully scoped to include only the momentum system's own changes — see git log 30e23d6.

Standing decision

Built, bug-fixed, and order-path-proven — autonomy still unconfirmed

The trading logic itself is correct and has placed a real, filled order on the paper account. But "the code is right" and "it will run unattended and reliably" turned out to be two very different claims this session — three separate infrastructure bugs (client ID, price collar, TWS stall) were each invisible until tested against live conditions, and the cron/sleep issue means zero unattended runs have succeeded as of this writing. A scheduled pre-market check is set for 8:30am ET the next trading day to get a real, current answer before assuming it's live.

The actual trading script has zero dependency on Claude Code or an active session — it runs entirely on OS cron + local Python + broker APIs. The scheduled check-ins and any future debugging do depend on it.
